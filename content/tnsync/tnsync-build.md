[[tnsync/tnsync-intro|앞 글]]에서 옵시디언 할일과 Todoist를 붙이는 데몬을 소개했다. 이 글은 만드는 과정이다.

먼저 결론부터. **양방향 동기화에서 어려운 건 데이터를 옮기는 게 아니다.** 옮기는 건 API 호출 몇 줄이다. 어려운 건 이거다.

**상대가 왜 그렇게 됐는지를 추측하는 것.**

Todoist에서 어떤 태스크의 날짜가 8월 1일에서 8월 8일로 바뀌었다고 하자. 사람이 미룬 건가, 완료해서 다음 회차로 넘어간 건가. **API는 알려주지 않는다.** 이 추측을 틀리면 없던 완료 기록이 생긴다. 실제로 생겼다.

## 단방향은 쉽다

먼저 왜 어려운지부터.

A에서 B로 밀기만 하는 건 간단하다. A를 읽고, B에 쓰고, 끝. B가 바뀌어도 다음 실행에 A 값으로 덮어쓰면 된다. **진실이 한 곳에만 있으니 고민할 게 없다.**

양쪽 다 편집 가능하게 만드는 순간 질문이 생긴다.

- 이 값이 바뀐 건가, 원래 저랬던 건가
- 양쪽 다 바뀌었으면 누가 이기나
- 내가 방금 반영한 변경이 다음 사이클에 반대로 돌아오지 않나

세 번째가 제일 고약하다. **무한 루프**다.

## 두 시스템을 하나의 모양으로 환원한다

기본 아이디어는 단순하다. TaskNotes 태스크와 Todoist 아이템을 **같은 모양의 딕셔너리**로 환원한다.

```
{ title, completed, due, scheduled, priority, tags[],
  project, parent, stage, duration, recurring }
```

변환 함수 두 개를 만든다. 하나는 마크다운 파일에서, 하나는 API 응답에서. **둘의 결과가 같으면 "동기화된 상태"다.** 그리고 그 딕셔너리를 정렬된 JSON으로 만들어 해시를 뜬 다음, 마지막으로 맞춘 시점의 해시로 저장해둔다.

다음 사이클에 다시 계산해서 비교한다.

| 상태 | 판정 |
|---|---|
| 양쪽 해시 그대로 | 아무것도 안 함 |
| 한쪽만 다름 | 그쪽에서 반대쪽으로 전파 |
| 양쪽 다 다름 | **충돌** |

이 구조의 좋은 점은 **필드가 늘어나도 로직이 안 바뀐다**는 것이다. 새 필드를 딕셔너리에 넣기만 하면 비교와 전파가 자동으로 따라온다.

## 에코 방지 — 무한 루프를 끊는 법

A를 B에 반영하면 B가 바뀐다. 다음 사이클에 "B가 바뀌었네" 하고 A로 되돌리고, 그게 다시 B로 가고, 영원히 돈다.

해결은 반영 직후에 **양쪽 해시를 합의된 값으로 함께 갱신**하는 것이다. 그러면 다음 사이클에 양쪽 딕셔너리가 같아서 아무 동작도 안 한다.

말은 쉬운데 실제로는 자꾸 샜다. 그래서 개발 내내 검증 기준을 하나로 고정했다.

**연속 세 번 실행했을 때 로그가 완전히 조용한가.**

뭔가 계속 찍히면 어딘가에서 에코가 돌고 있다는 뜻이다. 첫 실행이 조용한 건 의미가 없다. 두 번째, 세 번째까지 무음이어야 한다. 이 기준 하나가 버그를 여럿 잡아냈다.

## 충돌은 필드 단위로 안 푼다

양쪽이 동시에 바뀌면 수정 시각이 최신인 쪽이 이긴다. 그리고 승자는 **레코드 단위**로 정한다. 태스크 하나가 통째로 이기거나 통째로 진다.

필드 단위 병합이 더 똑똑해 보이는데 일부러 안 했다. **API가 필드별 수정 시각을 주지 않기 때문이다.** 어느 필드가 언제 바뀌었는지 모르는 채로 필드 단위 병합을 하면, 근거 없는 추측으로 데이터를 섞는 것이 된다. 그러다 양쪽 어디에도 없던 제3의 상태가 만들어진다.

**모르는 걸 아는 척하지 않는다.** 이게 이 도구 전체를 관통하는 원칙이 됐다.

## 상태 DB는 캐시일 뿐이다

SQLite를 하나 쓴다. 볼트 밖에 둔다. 테이블은 다섯 개고 연결 정보, 해시, Todoist 아이템 전체 미러, 프로젝트·섹션 캐시가 들어 있다.

여기서 정한 게 중요하다. **매핑의 원본은 DB가 아니라 마크다운 파일의 프론트매터다.**

```yaml
todoist_id: 8xxxxxxxxx
```

DB는 성능과 해시를 위한 캐시일 뿐이다. **통째로 날아가도 볼트 파일만 있으면 매핑이 재구성된다.** 동기화 도구가 자기 DB를 진실의 원천으로 삼으면, 그 DB가 깨지는 날 사용자 데이터도 같이 깨진다. 파일이 원본이면 최악의 경우에도 "다시 짝지으면 되는" 문제로 끝난다.

DB에서 유일하게 복구 불가능한 건 반복 작업의 기준선이다. 그게 없으면 그 공백 기간의 완료 델타가 전파되지 않는다. **가짜 완료가 생기지는 않고**, 현재 상태가 새 기준선이 된다. 잃는 쪽이 만드는 쪽보다 낫다고 판단했다.

Todoist 아이템 전체를 로컬에 미러링하는 이유도 적어둔다. Todoist의 증분 API는 **"변경분"만 준다.** 그런데 신규와 삭제를 판정하려면 전체 상태를 알아야 한다. 그래서 미러를 들고 증분으로 갱신한다.

## 순서가 로직이다

한 사이클은 아홉 단계다. 그리고 **이 순서 자체가 여러 버그의 해결책이다.**

1. Todoist 증분 동기화 → 캐시 갱신
2. 컨텍스트 주입 (섹션 맵, 제목→ID 역방향 맵)
3. 볼트 스캔 → 연결된 것 / 안 된 것 분류
4. 양쪽 연결된 쌍 조정
5. **볼트 쪽 삭제 감지** → Todoist에서 삭제
6. Todoist 쪽 삭제 감지 → 볼트 처리
7. 제목이 같은 것끼리 신규 연결
8. 신규 생성 (양방향)
9. 쌓인 쓰기 명령 일괄 전송

5번과 8번의 순서가 중요하다. 볼트에서 지운 태스크를 5번에서 Todoist에 삭제 요청하는데, 8번에서 **아직 갱신 안 된 캐시를 보고 "볼트에 없는 태스크가 있네" 하며 다시 만들어버렸다.** 같은 사이클 안에서 지우고 다시 만드는 것이다. 삭제한 ID를 8번의 생성 대상에서 명시적으로 제외하는 걸로 해결했다.

7번(제목 매칭)이 8번(생성)보다 앞인 것도 같은 이유다. 순서가 반대면 첫 실행에 모든 것이 중복 생성된다.

## 밟은 함정들

시간순으로 적는다. 대부분 조용히 틀리는 종류라서, 발견 자체가 늦었다.

**우선순위 오염.** Todoist의 3을 TaskNotes의 "medium"으로 매핑했다. **TaskNotes에 medium이라는 값이 없다.** 존재하지 않는 값이 프론트매터에 박히면서 조회 뷰에서 빠졌다. 상대 시스템의 값 목록을 문서가 아니라 설정 파일에서 확인해야 한다는 교훈.

**Inbox 에코.** Todoist 프로젝트를 만들어서 태스크를 넣으려고 했는데, 프로젝트를 생성하는 과정에서 태스크가 잠시 Inbox로 갔다. 그러면 딕셔너리에 "Inbox"가 섞이고, 다음 사이클에 "프로젝트가 다르네" 하고 다시 옮기고, 무한 업데이트가 났다. **프로젝트 생성 자체를 폐기하고 라벨로 표현하는 걸로 해결했다.** 우회가 정공법보다 안정적이었던 경우다.

**섹션 캐시가 비면 에코.** 증분 동기화는 이미 있던 섹션 정보를 안 준다. 그래서 캐시가 비어 있으면 태스크의 섹션이 "없음"으로 계산되고, 매 사이클 섹션을 다시 지정하려 든다. 캐시가 비면 한 번은 전체 동기화로 채우도록 고쳤다.

**duration 형식.** Todoist는 소요시간을 `{amount, unit}` 딕셔너리로 받는데 두 값을 따로 보냈다. API 오류 메시지가 불친절해서 한참 걸렸다.

여기까지는 평범한 버그다. 진짜는 반복 작업이었다.

## 반복 작업 — 여기서 제일 크게 데였다

두 시스템의 모델이 다르다. TaskNotes는 노트 하나에 **완료한 회차 목록**을 쌓는다. Todoist는 완료하면 **다음 날짜로 전진**한다. 같은 개념이 아니라 번역이 안 된다.

**반복을 완료했더니 반복이 끝났다.**

TaskNotes에서 반복 할일을 체크하면 Todoist에 완료 명령을 보냈다. 그런데 그 명령은 반복 태스크를 다음 회차로 넘기는 게 아니라 **히스토리로 보내 반복 자체를 종료시키는 것**이었다. 공식 클라이언트가 체크박스에 쓰는 명령은 따로 있었다.

이름만 보고 골랐다. API 문서에 "complete"라고 적힌 걸 쓰면 완료가 될 거라고 생각했는데, 반복 태스크에서는 의미가 달랐다. **공식 클라이언트가 실제로 무슨 명령을 보내는지 확인했어야 했다.**

**날짜를 미뤘을 뿐인데 없던 완료가 생겼다.**

이게 제일 크게 데인 것이다.

Todoist는 "완료해서 날짜가 넘어간 것"과 "사람이 손으로 미룬 것"을 **구분해서 알려주지 않는다.** 둘 다 그냥 "due가 바뀌었다"로 온다. 그래서 데몬이 전진을 완료로 착각하고 지나간 날짜를 완료 이력에 박았다.

여기에 증폭 장치가 하나 붙어 있었다. 데몬이 며칠 멈춰 있는 동안 여러 회차가 지나갔을 수 있으니, **건너뛴 중간 회차를 복원하는 기능**을 넣어뒀었다. 그래서 8월 1일을 12월 1일로 미뤘더니 **없던 완료가 네 건** 생겼다.

지금은 두 가지를 같이 본다. 새 날짜가 **반복 규칙상의 회차인가**, 그리고 **데몬이 그동안 살아 있었는가.** 규칙상 회차가 아니면 사람이 미룬 것이고, 규칙상 회차라도 여러 칸을 건너뛰었는데 데몬이 계속 돌고 있었다면 그것도 사람이 미룬 것이다. 데몬이 정말 오래 멈춰 있었다면 그때만 복원한다.

**추측이 필요한 곳에서는 추측이 틀렸을 때의 피해가 작은 쪽으로 기울여야 한다.** 완료를 놓치는 건 다시 체크하면 되지만, 없던 완료가 생기는 건 사용자가 알아채지도 못한다.

**규칙이 어긋나도 아무도 몰랐다.**

양쪽 반복 규칙이 달라질 수 있다. 그런데 어느 쪽이 최신인지 알 방법이 없다 — 또 그 얘기다, 필드별 수정 시각이 없다.

초기에는 그냥 Todoist 날짜를 계속 볼트로 끌어왔다. 그 결과 **노트가 자기 반복 규칙과 모순되는 상태**가 됐다. "매월 21일"이라고 적힌 노트의 다음 일정이 매월 1일인 식이다. 실제 반복 태스크 네 건 중 두 건에서 발생했다.

지금은 자동으로 안 맞춘다. 어긋난 걸 감지하면 **매 사이클 경고를 남기고, 사람이 고칠 때까지 그 태스크의 자동 갱신을 보류한다.**

```
WARNING 반복[…]: 규칙 불일치 — TaskNotes=…BYMONTHDAY=21 / Todoist='every 1st'
```

동기화 도구가 할 수 있는 최선이 "멈추고 알리기"인 경우가 있다.

**그리고 파서가 조용히 실패했다.**

Todoist에 "매월 1일"을 `every month on the 1st`로 보내면, Todoist가 그걸 `every 1st`로 정규화해서 돌려준다. 그런데 역변환 파서가 `month`라는 단어를 요구하고 있어서 인식에 실패했고, **반복 태스크가 일반 태스크로 만들어졌다.**

예외도 안 나고 로그도 안 남았다. 파싱 실패 시 `None`을 반환하고 호출부가 그걸 "반복 아님"으로 처리했기 때문이다. **파싱 실패와 "해당 없음"을 같은 값으로 표현하면 안 된다.**

## 완료일이 오늘로 덮인 사건

테스트하다가 완료 기록의 날짜가 전부 오늘로 덮인 적이 있다. 몇 달 치 완료 이력이 하루로 뭉개졌다.

살린 건 코드가 아니라 옵시디언의 **파일 복구** 기능이었다. 볼트 안 파일이라 스냅샷이 남아 있었고 무손실로 되돌렸다.

이게 "파일이 원본"이라는 설계의 두 번째 이득이다. 데이터가 서비스 DB 안에 있었으면 복구 방법이 없었다. **마크다운 파일이면 백업·복구·버전 관리를 이미 있는 도구들이 대신 해준다.**

## 안전장치

위 사고들을 겪으면서 붙인 것들이다.

**`--dry-run`.** 아무것도 쓰지 않고 계획만 로그로 찍는다. 로직을 바꿀 때마다 먼저 이걸로 돌린다.

**사이클 예외 격리.** 한 사이클이 예외로 죽어도 루프는 계속 돈다. 일시적인 네트워크 오류로 데몬이 통째로 멈추면, 그걸 알아채는 건 며칠 뒤다.

**유료 기능 자동 강등.** 유료 전용 필드에서 오류가 나면 그 필드를 빼고 재시도한다. 플랜에 따라 코드가 갈라지지 않게.

**모르면 손대지 않는다.** 부모 태스크가 아직 동기화 안 됐으면 하위 관계를 추측해서 채우지 않고 다음 사이클로 미룬다. 예전에는 그동안 임시로 라벨을 채워뒀는데, 기존 값을 덮어쓸 위험이 있어서 바꿨다.

**옵시디언 없이 테스트한다.** `scan` 명령은 토큰도 앱도 없이 볼트만 파싱해서 결과를 찍는다. 파싱 로직을 고칠 때 API를 부를 이유가 없다.

## 정리하면

만들면서 얻은 것 중 다른 데도 쓸 만한 것만 추린다.

**모르는 걸 아는 척하지 않는다.** 필드별 수정 시각이 없으면 필드 단위 병합을 하지 않는다. 부모를 모르면 하위 관계를 채우지 않는다. 규칙이 어긋나면 자동으로 맞추지 않고 멈춘다.

**추측이 틀렸을 때 어느 쪽 피해가 작은지로 기울인다.** 완료를 놓치는 것과 없는 완료를 만드는 것 중에서는 전자다.

**조용한 실패를 만들지 않는다.** 파싱 실패와 "해당 없음"이 같은 값이면 안 된다. 규칙이 어긋나면 매 사이클 경고를 낸다.

**검증 기준을 하나로 못박는다.** "연속 세 번 무음"이 이 프로젝트에서는 그 역할을 했다.

**원본을 파일에 둔다.** DB가 깨져도, 도구를 다시 짜도, 서비스를 옮겨도 파일은 남는다. 그리고 파일이면 이미 있는 백업·복구 도구가 전부 공짜로 붙는다.
