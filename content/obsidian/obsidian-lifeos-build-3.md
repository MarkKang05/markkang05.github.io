[[obsidian/obsidian-lifeos-build-1|1편]]에서 볼트의 폴더를 전부 지웠다. 대신 프론트매터 속성이 분류를 맡는다고 했고, 그 대가로 "속성을 철저히 관리해야 한다"고 썼다.

이 글이 그 청구서다.

## 속성을 늘리기 시작하면 폴더보다 나빠진다

폴더에는 자연스러운 제동장치가 있다. 하나만 고를 수 있으니까 고민이라도 한다. 속성에는 그게 없다. **필요해 보이는 필드를 계속 추가할 수 있고, 추가하는 순간에는 언제나 그럴듯해 보인다.**

책 노트에는 출판사와 ISBN이 필요할 것 같다. 프로젝트에는 시작일과 종료일이 있어야 할 것 같다. 스크랩에는 작성자가, 글에는 발행 플랫폼이. 이렇게 붙이다 보면 타입 열한 개에 필드가 쉰 개쯤 생기고, 그때부터는 **타입마다 다른 스키마를 가진 열한 개의 시스템**이 된다. 폴더를 프론트매터로 옮겨 적은 것뿐이다.

실제로 나도 그렇게 만들었다가 한 번 걷어냈다. 잘라낸 필드는 이렇다.

`project` `start` `related` `finished` `platform` `published` `author` `system` `severity`

이유는 두 가지 중 하나였다. **충족률이 0%였거나**(만들어놓고 아무도 안 채웠다), **다른 수단이 이미 하고 있었다.** `start`는 언제나 `created`와 같은 값이었다. `related`는 본문 `## 관련`의 링크가 이미 하던 일이다. `severity`는 심각도를 필드로 만들어봤자 본문 한 줄이 더 정확했다.

그래서 이 볼트의 스키마 설계는 **필드를 잘 만드는 규칙이 아니라 필드를 거절하는 규칙**이 본체다.

## 모든 타입이 공유하는 축 네 개

타입이 무엇이든 이 네 개는 똑같이 들어간다. **절대 갈라지지 않는다.**

```yaml
created: 2026-08-09          # 만든 날
persona: personal | work     # 나 / 회사
status: inbox | active | done | someday
tags: []
```

여기서 가장 중요한 게 `status`다.

예전에는 타입마다 어휘가 따로 있었다. 스크랩은 `unread`, 글은 `draft`, 이슈는 `발생`, 미디어는 `want`. 여섯 벌이었다. 결과는 뻔했다. **손은 제멋대로 쓰고 뷰는 죽었다.** "진행 중인 것 전부"를 보려면 필터에 여섯 개 조건을 or로 이어야 하는데, 그렇게 만든 뷰는 새 타입이 생길 때마다 고쳐야 한다.

지금은 네 단어 한 벌뿐이다. 덕분에 `status == "active"` 조건 하나가 **타입과 무관하게 "지금 살아 있는 것 전부"** 를 모은다. 대시보드의 첫 뷰가 이거고, 어휘를 통일했기 때문에 가능해진 뷰다.

뉘앙스는 본문에 쓴다. 이슈가 조치 중인지 복구됐는지는 본문 `## 조치`에 시각과 함께 적히지, `status`에는 안 들어간다.

그리고 하나 더. **`status`는 진행도가 아니다.** `inbox`는 "안 끝났다"가 아니라 **"내가 아직 안 봤다"**는 뜻이다. 이미 다 끝난 일을 적어놓은 노트도 검토 전이면 `inbox`다. 이 정의 덕분에 `status`가 뒤에 나올 큐레이션 루프의 작업 목록이 된다.

## 타입 열한 개

`type` 한 줄이 이 볼트의 스키마다. metadata-menu 플러그인의 `fileClassAlias`를 `type`으로 설정해두면, `type: media`라고 쓰는 순간 그 타입에 정의된 필드가 드롭다운으로 뜬다. 정의는 `_fileClasses/` 폴더에 타입마다 파일 하나씩 들어 있다.

| type | 전용 필드 | 무엇 |
|---|---|---|
| journal | date, mood(1–5) | 저널. 컨디션은 `mood`에만 |
| note | category(meeting/memo), series | 일반 노트와 회의록 |
| project | due | **끝나는 것**만 |
| media | category, rating, creator, cover | 책·영화·음악·게임 |
| scrap | source | 남이 쓴 것 |
| knowledge | maturity | **내가 써서 남긴 것** |
| entity | kind(person/system/org/place/area/asset) | **존재하는 것** |
| writing | kind(essay/blog/…) | 글. 버전은 한 파일에 `## V1.0` |
| issue | 없음 | 장애·생활 이슈 |
| moc | 없음 | 대시보드·인덱스 |
| publish | slug, tags | 사이트 공개본 |

나열이 목적은 아니고, 경계가 헷갈리는 것 몇 개만 보자.

**knowledge / scrap / entity.** 내가 배워서 쓴 것이면 `knowledge`, 남이 쓴 걸 담아둔 것이면 `scrap`, 배운 게 아니라 그냥 존재하는 것이면 `entity`. 세 개를 가르는 질문은 "이 문장을 누가 썼나"와 "이건 배운 것인가 있는 것인가"다.

**project / entity(area).** 프로젝트는 끝나고 area는 안 끝난다. 사내 시스템 운영이나 건강 관리처럼 영원히 계속되는 건 `project`가 아니라 `entity` + `kind: area`다. 대신 area에는 마감 대신 `## 범위`와 `## 유지 기준`을 붙인다. **유지 기준이 없는 area는 존재 이유가 없다.**

**이름이 있다고 entity가 아니다.** 소설 속 인물은 `person`이 아니다. 그건 `media` 노트 본문에 쓰고, 여러 작품에 걸쳐 반복되면 그때 `knowledge` 허브로 승격한다. 판별하는 질문 두 개 — **`status`를 채울 수 있는가. 백링크가 늘어나는가.**

**asset에는 평가액을 넣지 않는다.** 매달 변하는 숫자는 갱신이 끊기고, **낡은 숫자가 든 노트는 빈 노트보다 나쁘다.** 금액은 볼트 밖 스프레드시트에 두고, 노트에는 안 변하는 것만 적는다. 어디서 조회하는지, 만기가 언제인지, 해지하면 뭘 잃는지, 서류가 어디 있는지. 그래서 자산 노트는 연금·보험·부동산처럼 맥락이 있는 것만 만든다. 예금 통장은 스프레드시트 한 줄이지 노트가 아니다.

## 필드 하나를 늘리려면

새 필드는 세 관문을 다 통과해야 한다. 하나라도 걸리면 본문이나 링크로 간다.

1. **기존 수단으로 대체 불가능한가.** `created`, `status`, `tags`, `## 관련`의 링크, 그리고 본문. 이 다섯 개가 이미 그 일을 하고 있지 않은가.
2. **낡지 않는가.** 시간이 지나면 틀려지는 값인가.
3. **타입 전체에 해당하는가.** 특정 하위 분류만을 위한 필드인가.

이 심사를 통과한 필드는 지금까지 하나뿐이다. `media.cover`(표지).

- **대체 불가능한가** → 그렇다. Bases 카드뷰의 이미지는 **프론트매터 속성만 읽는다.** 본문에 `![[표지.jpg]]`를 아무리 넣어도 카드에는 안 뜬다. 다른 수단이 없다.
- **낡지 않는가** → 그렇다. 표지는 한 번 정해지면 안 변한다. 자산의 평가액과 정반대 경우다.
- **타입 전체인가** → 그렇다. 책 표지, 영화 포스터, 앨범 커버, 게임 키아트. **책만을 위한 필드였다면 안 넣었다.** `media`를 category별로 쪼개는 첫 단추가 됐을 것이다.

그리고 필드를 지우는 건 절반만 일이다. 타입 정의에서 지우고 끝이 아니라 **템플릿과 모든 조회 뷰의 컬럼·필터에서도 같이 지워야 한다.** 안 그러면 없는 필드를 참조하는 뷰가 조용히 빈칸을 뱉는다.

## 태그를 분류에 안 쓰기로 했다

가장 반직관적인 결정이라 따로 뗀다.

옵시디언에서 태그는 보통 주제 분류로 쓴다. 나는 그걸 두 번 시도하고 두 번 실패했다. 처음엔 어휘를 아홉 개로 닫아놓고 그중에서 고르게 했고, 그다음엔 자유 입력으로 풀었다. 둘 다 같은 이유로 실패했다. **"이 노트의 주제는 무엇인가"는 답하기 어려운 질문이고, 답이 안 나오면 그냥 안 붙이게 된다.**

그래서 실제로 붙어 있던 태그를 전수 조사했다. 21건이었고, 결과가 명확했다.

| 태그 | 건수 | 실체 |
|---|---|---|
| `todoist-sync` | 9 | 동기화 문서 시리즈 — **허브 노트가 이미 있었다** |
| `커리어` | 9 | 자소서·면접 노트 — **허브가 없어서 태그가 유일한 끈이었다** |
| 나머지 | 3 | 단발 |

**21건 중 18건이 "같은 시리즈 묶기"였다.** 도메인 분류로 쓰인 태그는 사실상 없었다. 손이 실제로 하던 일은 분류가 아니라 묶기였던 것이다.

그래서 태그를 그 일로 다시 정의했다. **태그 = 허브 노트가 아직 없는 시리즈의 임시 이름표.**

- 규칙은 하나. "이 노트들을 나중에 같이 찾겠다" 싶을 때만 붙인다
- 값은 아무 단어나. **안 떠오르면 안 붙인다.** 빈 `tags: []`가 기본이고 정상이다
- 같은 태그가 세 개를 넘으면 **허브 노트를 만들고 태그는 지운다**
- 이름이 붙은 것(시스템·프로젝트·사람·벤더)은 태그가 아니라 `## 관련`의 링크다
- 타입·상태·persona·연도는 프론트매터에 이미 있다. 태그로 중복하지 않는다
- 계층 태그(`#work/saas`)는 안 쓴다. `persona`가 이미 그 축이다

허브 노트가 태그보다 나은 이유는 단순하다.

| | 태그 `#todoist-sync` | 허브 노트 `Todoist 동기화` |
|---|---|---|
| 모으는 것 | 같은 노트들 | 같은 노트들 |
| 설명을 쓸 자리 | **없다.** 문자열이다 | 있다 — 요약·순서·맥락 |
| 시작점 | 없다. 목록만 나온다 | **그 노트를 열면 된다** |

정리 결과 태그 21건을 전부 제거하고 허브 노트 하나를 새로 만들었다. 지금 이 볼트에서 태그가 붙은 노트는 거의 없다. 그게 정상 상태다.

## persona — 나와 회사를 한 볼트에

업무와 개인을 볼트 두 개로 나누지 않고 필드 하나로 나눴다. 값은 `personal`과 `work` 두 개뿐이고, 세 개 이상으로 쪼개지 않는다.

기본값은 만든 시각으로 자동 결정된다. **평일 08:00~17:59면 `work`, 그 외에는 `personal`.** 로직은 Templater 사용자 스크립트 한 파일에 들어 있다.

```js
function persona() {
  const now = moment();
  const isWeekday = now.day() >= 1 && now.day() <= 5;
  const isWorkTime = now.hour() >= 8 && now.hour() < 18;
  return isWeekday && isWorkTime ? "work" : "personal";
}
```

사람에게 묻지 않는 게 핵심이다. 물으면 그 질문 자체가 마찰이고, **틀려도 나중에 고치면 되는 값**이기 때문이다. 근무시간이 바뀌면 이 파일 한 곳만 고치면 모든 템플릿에 반영된다.

한 가지 더. **공개용 값(`public`)은 만들지 않았다.** persona는 "이게 어디서 나왔나"(출신)를 묻는 축인데 공개는 "누가 읽나"(청중)의 문제다. 축이 직교하는데 같은 필드에 넣으면 한 필드가 두 질문에 답하게 되고, 공개본의 출신을 물을 수 없게 된다. 공개는 `publish`라는 별도 타입이 맡는다(8편).

## 사소하지만 물리는 것들

프론트매터를 쓰다가 실제로 데인 것들이다.

**숫자에 따옴표를 붙이지 않는다.** `mood: "3"`은 문자열로 파싱되어 조회 테이블에서 좌측 정렬로 튄다(숫자는 우측 정렬). 눈에 잘 안 띄는데 정렬도 이상해진다. 세 건 발견해서 고쳤다.

**빈 값은 키를 남기고 값만 비운다.** `mood:`처럼. 키를 통째로 지우면 편집기에서 그 칸이 안 보여서 나중에 채우지 않게 된다.

**템플릿 파일 안에서는 치환 토큰을 따옴표로 감싼다.** `date: "{{date:YYYY-MM-DD}}"`. 안 그러면 YAML이 깨진다.

## 대가

정직하게 적자면, 이 설계는 앞에서 말한 대가를 그대로 청구한다.

속성을 안 채우면 노트는 어떤 뷰에도 안 잡히는 유령이 된다. 폴더 시절의 "일단 아무 데나 넣어두기"에 해당하는 도피처가 없다. 그리고 이 볼트에서 노트를 만드는 빈도를 생각하면, **매번 손으로 채우는 건 애초에 불가능하다.**

그러니 자동화가 선택이 아니라 전제 조건이다. 다음 편은 그 얘기다. 새 노트를 만들 때 실제로 무엇을 고르고 무엇이 자동으로 채워지는지.
