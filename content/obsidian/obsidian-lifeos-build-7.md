[[obsidian/obsidian-lifeos-build-1|1편]]에서 다른 앱을 포기한 이유가 커스터마이징 한계였다. 옵시디언을 골랐다는 건 그 한계를 직접 넘겠다는 뜻이기도 했다.

이 글은 그래서 실제로 뭘 만들었는지에 대한 것이다. CSS 스니펫 일곱 개, 플러그인 두 개, 남의 플러그인 패치 하나.

## 원칙 하나 — 설정보다 파일

들어가기 전에 기준부터. 플러그인 설정 화면에서 되는 일이라도, **`.base` 파일이나 CSS 스니펫으로 할 수 있으면 그쪽을 고른다.**

이유는 셋이다. 설정은 앱 안에 갇혀 있어서 **git에 안 남는다.** 그러니 언제 왜 바꿨는지 추적이 안 된다. 그리고 **주석을 달 수 없다.** 반년 뒤에 "이 값이 왜 34px이지" 하고 보면 답이 없다.

파일은 반대다. diff가 나오고, 맨 위에 이유를 적을 수 있고, 필요 없어지면 파일 하나 지우면 끝난다.

## CSS 스니펫 — 원칙 세 개

스니펫은 `.obsidian/snippets/`에 두고 설정 → 모양에서 켠다. 파일을 새로 만들면 켜는 걸 잊기 쉬우니 주의.

지키는 규칙이 셋이다.

**한 파일 = 한 목적.** 이름만 보고 뭘 건드리는지 알 수 있어야 하고, 필요 없어지면 파일 하나만 지우면 끝나야 한다. 하나의 `custom.css`에 다 몰아넣으면 나중에 뭘 지워야 할지 모른다.

**적용 범위를 셀렉터로 좁힌다.** 기기(`.is-mobile`), 특정 노트(`cssclasses`), 플러그인 뷰 단위로 가둔다. 전역으로 뿌리면 나중에 무엇이 무엇을 깨뜨렸는지 못 찾는다.

**조절 지점은 파일 맨 위 변수로.** 숫자를 고치러 CSS 본문을 읽지 않아도 되게.

```css
body {
  --tn-hr-thickness: 3px;
  --tn-hr-color: var(--color-base-40);
}
```

## 실제로 켜둔 것들

지금 여섯 개가 돌고 있다. 전부 설명하지 않고 성격이 다른 것만 골라 적는다.

**readable-line-width — 데스크탑만 850px.**

옵시디언의 "읽기 쉬운 행 길이"는 기본 700px인데 넓은 화면에서는 너무 좁다. 그런데 모바일은 기본값이 맞다. 그래서 데스크탑에만 건다.

```css
body:not(.is-mobile) {
  --file-line-width: 850px;
}
```

두 줄짜리지만 "범위를 좁힌다"의 교과서 같은 예다. 전역으로 걸었으면 아이패드에서 본문이 화면 밖으로 나갔을 것이다.

**compact-bases-header — 아이패드 전용 높이 압축.**

아이패드는 세로 공간이 좁은데, 조회 뷰를 열면 헤더가 삼중으로 쌓인다. 탭 바 40px + 파일 경로 행 40px + Bases 툴바 52px. 아무것도 안 보여주면서 130px을 먹는다.

`.is-mobile`로 가두고 각각 32px, 34px, 34px로 줄이고 아이콘도 16px로 낮췄다. 데스크탑은 손대지 않으니 기본값 그대로다.

**table-grid — 원칙을 일부러 어긴 것.**

마크다운 표는 기본적으로 행 구분선만 있고 열 구분이 없다. 셀 하나에 **여러 줄짜리 목록**이 들어가면 어느 항목이 어느 열인지 눈으로 못 따라간다. 6편의 감사·걱정 표가 정확히 그 경우다.

그래서 모든 셀에 테두리를 넣었다. 그런데 이건 **전역으로 걸었다.** "범위를 좁힌다"는 원칙에 어긋난다.

일부러 그랬다. 격자는 특정 노트가 아니라 **표라는 형식 전체**에 일관되게 적용되어야 읽기 규칙이 생긴다. 어떤 표는 격자고 어떤 표는 아니면 그게 더 산만하다. 원칙을 어길 때는 어긴다는 걸 알고 이유를 적어두면 된다.

**tasknotes-none-column — 플러그인의 정규 옵션이 안 먹어서.**

할일 칸반을 상태로 그룹핑하면 **설정에 등록된 모든 상태가 빈 컬럼으로 미리 깔린다.** 상태 목록 첫 항목이 "None"이라, 실제로 None인 할일이 0건이어도 빈 칸이 항상 맨 앞에 뜬다.

이걸 막는 정규 수단은 뷰 옵션 하나뿐인데, `.base` 파일에 넣은 옵션이 반영되지 않았다. 그래서 CSS로 우회했다.

```css
.tasknotes-plugin .kanban-view__board .kanban-view__column[data-group="none"] {
  order: 999;
}
```

보드가 flex라서 `order`만 주면 맨 오른쪽으로 밀린다. 완전히 숨기려면 `display: none`으로 바꾸면 되는데, 밀어두기만 해도 충분해서 그대로 뒀다.

근본 해결은 설정에서 "None" 상태 자체를 지우는 것이다. 그러면 시드가 사라져 어느 뷰에서도 안 뜬다. 부작용은 상태 순환에서 none이 빠지는 것뿐인데 어차피 안 쓰는 값이다. 그런데 **CSS는 설정과 무관하게 동작하고 git에 남는다.** 그래서 CSS 쪽을 택했다.

## 제일 크게 데인 것 — 편집 화면에 margin 금지

만들어놓고 지금은 꺼둔 스니펫이 하나 있다. `heading-band`, `##` 제목을 회색 띠로 만드는 것이다.

본문 섹션이 고정된 타입(이슈의 증상/원인/조치, 회의록의 안건/논의/참석자, 주간 노트)에서 헤딩 크기만으로는 경계가 안 보인다. 그래서 띠를 둘렀다. 여기까지는 CSS 몇 줄이다.

**그런데 편집 화면에서 클릭이 어긋나기 시작했다.**

`##` 제목을 지날 때마다 커서가 한 행쯤 아래로 찍혔다. 클릭한 자리와 캐럿이 들어가는 자리가 다르다. 링크나 버튼은 멀쩡했다.

원인을 찾는 데 한참 걸렸다. 옵시디언의 편집기는 CodeMirror 6인데, **줄 높이를 `offsetHeight`로 캐시한다.** 이 값에는 padding과 border는 포함되지만 **margin은 포함되지 않는다.** 그래서 `.cm-line`에 margin을 주면 화면상의 실제 위치와 에디터가 계산하는 좌표가 어긋난다. 링크와 버튼이 멀쩡했던 건 그건 실제 DOM 요소라 브라우저가 직접 처리하기 때문이고, **그 멀쩡함이 오히려 원인 찾기를 방해했다.**

해결은 여백을 margin 대신 **투명 border**로 만드는 것이다.

```css
.markdown-source-view.mod-cm6 .HyperMD-header-2 {
  border-top: 2.2em solid transparent !important;
  border-bottom: 0.9em solid transparent !important;
  background-clip: padding-box;
}
```

`background-clip: padding-box`는 회색 띠가 투명 border 영역까지 번지지 않게 하는 것이다. 읽기 화면은 CodeMirror가 아니니 거기만 margin을 쓴다.

교훈은 하나로 정리된다. **`.cm-line` 계열(`.HyperMD-*`, `.cm-line`, `.cm-content > *`)에 margin·transform·position을 걸지 말 것.** 걸면 같은 증상이 난다.

참고로 이 스니펫은 지금 꺼져 있다. 문제는 해결했지만 화면이 다소 무거워져서 잠시 내려둔 상태다. 코드와 그 안의 주석은 남겨뒀다. **같은 함정을 다시 밟지 않으려면 코드보다 주석이 자산이다.**

## 캘린더가 노트를 못 찾던 버그

CSS는 아니지만 추적 과정이 비슷해서 같이 적는다.

**증상.** 달력에서 날짜를 눌러도 이미 있는 일간 노트를 못 찾고 "새로 만들까요?"를 묻는다. 주간 노트는 정상이다.

**원인.** 캘린더 플러그인은 파일명을 moment의 **엄격 모드**로 파싱한다.

```js
const noteDate = window.moment(file.basename, format, true);
```

일간 파일명 형식은 `YYYY-MM-DD (ddd)`이고, 여기서 `ddd`(요일)는 **로케일에 따라 결과가 달라지는 토큰**이다. 옵시디언 UI 언어가 한국어면 moment 로케일도 한국어가 되고, 그러면 `ddd`는 `(수)`를 기대한다. 파일명은 `(Wed)`니까 파싱에 실패한다. 주간 파일명(`2026-W32`)에는 로케일 의존 토큰이 없어서 멀쩡했던 것이다.

**조치.** 설정 → Calendar → Override locale을 `en`으로. 노트는 하나도 안 건드렸다.

**`en-gb`를 쓰면 안 되는 이유가 있다.** 이 설정은 moment 로케일을 **전역**으로 바꾼다. 주간 파일명의 주차 번호는 로케일의 "주 시작 요일"을 따르는데, 한국어와 `en`은 둘 다 일요일 시작이라 기존 주간 노트 파일명이 그대로 유지된다. `en-gb`는 ISO 표준(월요일 시작)이라 주차가 한 칸씩 밀려서 **기존 주간 노트를 전부 못 찾게 된다.** 로케일 하나 바꾸는 데 이만큼 확인이 필요하다.

**덤으로 발견한 것.** 엄격 모드는 요일과 날짜의 정합성까지 검사한다. 일간 노트 51개를 전수 검사했더니 `2026-04-11 (Tue)`가 하나 있었다. 실제로는 토요일이다. **요일이 틀린 파일은 로케일과 무관하게 달력에서 영영 안 잡힌다.** 에러도 안 나고 그냥 조용히 없는 노트가 된다.

저널 파일명의 요일을 손으로 고칠 일이 생기면 날짜와 맞는지 반드시 확인해야 한다.

## 남의 플러그인을 패치했다

검색에서 한글로 치고 `↓`를 누르면 **1행에서 3행으로 건너뛴다.** 2행이 선택되지 않는다. `↑`는 정상이고, 영문 검색도 정상이고, 윈도우와 모바일에서는 재현되지 않는다.

원인은 IME(한글 입력기) 조합 상태였다.

Omnisearch는 조합 중인지 아닌지를 플래그로 들고 있다. 그런데 그 플래그를 **`Enter` 키에서만 검사하고 화살표 키에서는 검사하지 않는다.**

```js
this.scope.register(n, "Enter", d => { Sp() || (...) });   // 가드 있음
this.scope.register([], "ArrowDown", d => { ... });        // 가드 없음
```

macOS 한글 입력기는 마지막 글자를 조합 중으로 유지한다. 그래서 `↓` 한 번이 **조합 확정용 keydown + 확정 후 keydown** 두 번으로 전달된다. 가드가 없으니 이동 이벤트가 두 번 발행되고, 이동 함수가 델타를 그대로 더해 +1 +1 = +2가 된다. `↑`가 정상인 이유는 그 시점엔 조합이 이미 끝나서 keydown이 한 번만 오기 때문이다.

패치는 `Enter`와 같은 가드를 화살표에도 붙이는 것이다. 실제 변경은 **16바이트**다.

문제는 이게 빌드된 `main.js`라 **플러그인을 업데이트하면 되돌아간다**는 것이다. 그래서 패치 스크립트를 문서로 남겨뒀다. 난독화된 변수명이 버전마다 바뀌므로 이름을 하드코딩하지 않고, `Enter` 등록부에서 가드 함수 이름을 역추출해서 쓴다. 이미 패치돼 있으면 아무것도 안 하고, 패치 지점을 못 찾으면 파일을 안 건드린다.

주의할 게 하나 있다. **`.obsidian/plugins/`는 옵시디언 동기화로 다른 기기에 전파된다.** 좋은 소식은 한 기기에서만 패치하면 된다는 것이고, 나쁜 소식은 **어느 한 기기에서 플러그인을 업데이트하면 패치 안 된 버전이 전체로 퍼진다**는 것이다. 증상이 다시 보이면 그 경우다.

패치 없이 피하는 방법도 있다. 설정에서 Vim 방식 이동을 켜면 `Ctrl+J`/`Ctrl+K`로 움직일 수 있는데, 조합기를 거치지 않는 조합키라 이 문제를 안 만난다.

그리고 아직 안 한 일이 있다. **상류에 이슈를 안 올렸다.** 원인 분석은 이미 다 해놨으니 영문으로 옮기면 그대로 리포트가 된다. 그러면 이 패치를 계속 들고 다닐 필요가 없어진다. 남의 코드를 고쳐서 쓰는 건 임시방편이고 임시방편에는 유효기간이 있다.

## 플러그인 두 개를 만들었다

**korean-book-search.** 교보문고와 YES24에서 검색해서 책 노트를 만든다.

특이한 점은 **Templater 템플릿을 안 쓴다**는 것이다. 프론트매터와 본문 형식을 전부 플러그인 설정 칸에 넣고 템플릿 파일은 비워뒀다. 책 노트 하나 때문에 `Templates/` 폴더에 파일을 늘리지 않으려고 그랬다.

그러려면 플러그인을 두 군데 고쳐야 했다.

- 날짜 치환이 **템플릿 파일에만** 적용되고 설정 칸에는 적용되지 않았다. 안 고치면 `created: {{date:YYYY-MM-DD}}`가 그냥 지워진 채로 노트가 만들어진다.
- 빈 값을 `rating: ""`으로 내보냈다. 빈 문자열은 숫자·선택 속성을 문자열로 오염시켜 **조회 뷰의 정렬을 깬다.** 3편에서 말한 `mood: "3"` 문제와 같은 종류다. `rating:`(빈 값)으로 나가게 고쳤다.

서지 정보(출판사·ISBN·쪽수·원제·역자·링크·책소개)는 전부 본문 `## 서지`로 보낸다. **책 때문에 `media` 타입에 필드를 늘리지 않기 위해서다.** 표지만 예외로 프론트매터에 있고, 그 이유는 5편에서 적었다.

**quartz-publish.** 볼트의 공개 글을 블로그로 내보내는 도구다. 이게 8편 주제라 여기서는 하나만 적는다.

이 플러그인은 **볼트 안에 산다.** `.obsidian/plugins/quartz-publish/`에 직접 들어 있어서 별도 저장소도 빌드 과정도 없다. `main.js`를 고치고 앱을 새로고침하면 끝이다. TypeScript도 번들러도 안 쓴다.

작은 개인용 도구에 빌드 파이프라인을 붙이면 **고치는 비용이 올라가서 안 고치게 된다.** 지금은 버그를 발견하면 그 자리에서 30초 만에 고친다.

## 만들기 전에 따지는 순서

직접 만드는 건 재미있지만 유지보수가 따라붙는다. 그래서 순서를 정해뒀다.

1. **이미 있는 기능 두 개를 겹칠 수 있나** — 아이젠하워 매트릭스가 여기서 풀렸다. 우선순위 네 단계 + 칸반 그룹핑
2. **`.base` 파일로 되나** — 조회는 거의 다 여기서 끝난다
3. **CSS 스니펫으로 되나** — 보이는 문제는 대개 여기
4. **플러그인 설정으로 되나** — 캘린더 로케일이 이 경우
5. **남의 플러그인을 고쳐야 하나** — Omnisearch. 업데이트마다 재적용 비용이 붙는다
6. **직접 만들어야 하나** — 마지막

아래로 갈수록 비용이 커진다. 5번부터는 **내가 안 만든 코드를 계속 따라다녀야 하는 부채**가 생기고, 6번은 만든 뒤에도 끝나지 않는다.

그래도 1~4번에서 대부분이 끝난다는 게 이 순서의 요점이다. 옵시디언에서 "플러그인이 없어서 못 한다"고 느낄 때, 실제로는 이미 있는 것 두 개를 겹치면 되는 경우가 많다.
