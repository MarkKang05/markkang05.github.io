폴더를 지웠다고 하면 제일 먼저 나오는 질문이 이거다.

**"그럼 어떻게 찾아요?"**

이 글이 그 답이다. [[obsidian/obsidian-lifeos-build-1|1편]]에서 없앤 것의 값을 여기서 회수한다.

## 폴더는 뷰 하나를 굳혀놓은 것이다

관점을 뒤집어 보자.

`Media/Books/읽는 중/`이라는 폴더는 결국 **"type이 media이고, category가 book이고, status가 active인 노트"** 라는 조회 조건을 디렉터리 구조로 굳혀놓은 것이다. 폴더가 나쁜 게 아니라, **굳혔기 때문에 다른 관점이 불가능해진 것**이 문제다.

Bases는 그 조회를 파일 이동 없이 몇 개든 만든다. 노트는 하나고, 관점만 늘어난다.

Bases는 옵시디언 1.9에 들어온 코어 기능이다. `.base` 파일 하나에 필터와 뷰를 YAML로 적어두면 표나 카드로 렌더된다. 플러그인이 아니라 코어라는 게 중요하다. **버전이 올라가도 안 깨지고, `.base`는 그냥 파일이라 git에 남는다.**

## 실제로 쓰는 뷰

지금 볼트에 있는 `.base` 파일은 여섯 개다. 각각이 답하는 질문이 다르다.

**`탐색기.base` — 파일 트리를 대체하는 것.**

뷰가 서른 개 넘게 들어 있다. 크게 세 묶음이다.

- **통합** — 전체 / 인박스 / 진행중 / 타입별(note, 회의록, project, knowledge, entity, scrap, media, writing, issue, journal, moc, publish) / 도면
- **personal** — 개인 것만 같은 방식으로
- **work** — 회사 것만 같은 방식으로

"통합 · 전체"는 `type`으로 그룹핑해서 보여준다. 이게 사실상 예전 폴더 트리의 자리를 대신한다. 다만 폴더와 달리 옆에 `persona`, `status`, `created`, 수정일이 같이 뜬다. **트리는 이름만 보여주지만 뷰는 상태를 보여준다.**

**`inbox.base` — 아직 안 본 것.**

`status == "inbox"` 하나로 필터하고 `type`으로 그룹핑한다. 이게 큐레이션의 작업 목록이다(6편에서 다룬다).

**`Home.base` + `Dashboard.md` — 하루 시작 화면.**

진행 중인 프로젝트, 인박스 노트, 회사 것 전부, 감상 중인 미디어, 안 읽은 스크랩, 지식, 미발행 초고. 뷰 일곱 개가 한 파일에 들어 있고 `Dashboard.md`가 그걸 임베드한다. 앱을 켜면 이 노트가 열린다.

여기서 3편의 결정이 값을 한다. `status` 어휘를 전 타입 한 벌로 통일했기 때문에 **`status == "active"` 조건 하나가 타입과 무관하게 "지금 살아 있는 것 전부"를 모은다.** 어휘가 타입마다 달랐다면 이 뷰는 존재할 수 없다.

**`탐색기 (work).base` / `탐색기 (personal).base` — persona 분리.**

각각 인박스 뷰를 따로 갖는다. 회사 인박스와 개인 인박스를 섞어놓으면 정리할 마음이 안 생긴다.

여기에 규칙이 하나 있다. **어느 뷰에 들어갈지는 `persona` 필드가 있느냐가 아니라 "그게 내 삶의 내용인가"로 정한다.** 저널과 미디어는 `persona` 필드 자체가 없지만 개인의 내용이라 personal 뷰에 `or` 조건으로 넣었다. 반대로 `moc`(대시보드·인덱스)와 `publish`(사이트 원고)는 볼트를 굴리기 위한 운영 타입이라 **통합 뷰에만** 둔다. persona 분리 뷰에 넣으면 같은 행이 두 곳에 중복되고 유지할 곳만 늘어난다.

## 서재 — 표지 때문에 필드를 하나 늘렸다

`서재.base`는 유일한 카드 뷰다. 책 표지가 격자로 깔리고 `status`로 그룹핑된다.

```yaml
filters:
  and:
    - type == "media"
    - category == "book"
views:
  - type: cards
    image: note.cover
    imageAspectRatio: 1.6
    cardSize: 160
```

3편에서 "필드는 자르는 게 원칙"이라고 해놓고 유일하게 통과시킨 게 `cover`인데, 그 이유가 이 네 줄이다. **카드 뷰의 `image:`는 프론트매터 속성만 읽는다.** 본문에 이미지를 아무리 넣어도 카드에는 안 뜬다. 다른 수단이 없어서 필드가 됐다.

표지는 서점 URL이 아니라 **로컬에 저장한다.** 서점 링크는 언젠가 썩고, 파일당 수십 KB라 저장소 부담도 없다. 그리고 **한 장을 두 군데 두지 않는다** — 프론트매터에만 넣고 본문에는 안 넣는다. 두 군데 두면 언젠가 갈라진다.

`imageAspectRatio: 1.6`은 책 표지 비율이다. 기본값으로 두면 세로로 긴 표지가 잘린다.

## 아이젠하워 매트릭스 — 있는 것 두 개를 겹쳤다

제일 마음에 드는 뷰다. 그리고 새로 만든 게 거의 없다.

할일 플러그인의 우선순위가 이미 네 단계로 정의돼 있다.

| 값 | 라벨 | 색 |
|---|---|---|
| P1 | 중요, 급함 | 빨강 |
| P2 | 중요, 안 급함 | 주황 |
| P3 | 안 중요, 급함 | 초록 |
| P4 | 안 중요, 안 급함 | 회색 |

**이미 아이젠하워 매트릭스다.** 라벨을 저렇게 지어놨을 뿐 구조가 같다. 그러면 칸반 보드를 우선순위로 그룹핑하고 **컬럼 네 개를 2×2 격자에 가두기만 하면** 그대로 매트릭스가 된다.

칸반 뷰는 그냥 만들면 되고, 격자는 CSS 스니펫 스물몇 줄이다.

```css
.eisenhower .kanban-view__board {
  display: grid;
  grid-template-columns: 1fr 1fr;
  grid-template-rows: 1fr 1fr;
  height: clamp(440px, calc(100vh - 260px), 920px);
  overflow: hidden;
}
```

핵심은 마지막 두 줄이다. **높이를 화면에 맞춰 고정하고 보드 자체는 스크롤하지 않는다.** 항목이 아무리 많아도 칸이 늘어나지 않고 그 칸 안에서만 스크롤된다. 매트릭스는 네 칸의 크기 비교가 정보인데, 칸이 내용만큼 늘어나면 그 정보가 사라진다.

여기서 한 번 크게 헤맸다. 격자를 만들었는데도 칸이 계속 늘어났다. 원인은 이거였다.

```css
.eisenhower .kanban-view__column {
  min-height: 0;
  min-width: 0;
}
```

**CSS 격자의 자식은 기본적으로 내용보다 작아지지 않는다.** `min-height`의 기본값이 `auto`라서 그렇다. 이걸 `0`으로 명시해야 비로소 부모가 정한 높이를 따른다. 그 안의 카드 영역도 마찬가지로 `min-height: 0`을 줘야 한다. 격자나 플렉스로 스크롤 영역을 만들 때 거의 항상 물리는 함정이다.

나머지는 마감이다. 사분면 제목은 스크롤해도 위에 붙어 있게 하고(`position: sticky`), 컬럼 위쪽에 우선순위 색과 같은 3px 띠를 두르고, 드래그로 옮기는 중인 칸은 점선으로 강조한다. 아이패드 세로 화면에서는 2×2가 너무 좁아서 1열 4행으로 바꾼다.

```css
@media (max-width: 700px) {
  .eisenhower .kanban-view__board {
    grid-template-columns: 1fr;
    grid-template-rows: repeat(4, minmax(160px, 1fr));
  }
}
```

## 화면 배치를 통째로 저장해뒀다

뷰가 많아지면 다음 문제가 생긴다. **어느 뷰를 어디에 띄울 것인가.**

옵시디언 코어의 작업 공간(Workspaces) 기능으로 레이아웃을 통째로 저장해두고 `⌘0`으로 갈아끼운다. 지금 일곱 개다.

| 이름 | 화면 구성 |
|---|---|
| 1. 업무 | 메인에 `탐색기 (work)` + 할일 목록 + 홈, 오른쪽에 캘린더 |
| 2. 개인 | 메인에 `탐색기 (personal)` + 할일 목록 + 홈 |
| 3. 캘린더 | 메인 전체가 할일 캘린더 뷰 |
| 4. 칸반 | 메인 전체가 칸반 보드 |
| 5. 베이직 | 노트 하나만. 사이드바 기본 |
| 6. 데스크탑 | 메인에 `탐색기` + 할일 + 빈 탭 + **터미널** |
| 6. 랩탑 | 메인은 터미널만, **Bases를 왼쪽 사이드바로 옮김** |

데스크탑과 랩탑을 나눠둔 이유가 이 방식의 핵심이다. 화면이 좁아지면 조회 뷰를 메인에 두기가 아까워진다. 그래서 랩탑에서는 **같은 `.base` 파일을 왼쪽 사이드바에 넣는다.** 뷰를 다시 만드는 게 아니라 **같은 뷰를 다른 자리에 놓는 것**이고, `.base`가 파일이라 어디에든 띄울 수 있어서 가능하다.

업무와 개인을 나눈 것도 같은 이유다. 회사에서 개인 노트가 눈에 들어오면 신경이 쓰이고, 반대도 마찬가지다. 볼트를 나누지 않고 **보는 창만 나눴다.**

## 탐색은 검색이 한다

폴더 트리를 훑는 행위가 사라지면 그 자리를 검색이 채운다. Omnisearch를 `⌘O`에 걸어뒀다.

기본 전문 검색과 다른 점은 **가중치를 줄 수 있다**는 것이다. 지금 이렇게 맞춰놨다.

| 대상 | 가중치 |
|---|---|
| 파일명 | 10 |
| 폴더명 | 7 |
| H1 | 6 |
| H2 | 5 |
| H3 | 4 |

파일명이 압도적으로 높다. 파일명이 곧 제목인 볼트라 대부분의 검색은 제목을 기억해내는 일이기 때문이다. 오타 허용치도 1로 켜뒀다.

한글 입력에서 화살표 이동이 두 칸씩 튀는 버그가 있어서 직접 패치한 적도 있는데, 그 얘기는 7편에서 한다.

## 안 되는 것

**뷰는 속성이 정확할 때만 작동한다.** 3편에서 말한 대가가 여기서 청구된다. `type`을 안 적은 노트는 어느 뷰에도 안 잡힌다. 폴더라면 최소한 어딘가에는 있는데, 속성이 비면 정말로 없는 것이 된다.

**필드를 지울 때 뷰도 같이 고쳐야 한다.** 타입 정의에서 필드를 빼고 끝내면, 그 필드를 컬럼으로 쓰던 뷰가 조용히 빈칸을 뱉는다. 에러가 안 나서 한참 모른다.

**그리고 실제로 그 일이 이미 일어나 있다.** 이 글을 쓰면서 `Home.base`를 열어봤더니 뷰 세 개가 죽어 있었다.

```yaml
- type == "media"
- status == "doing"      # 지금 어휘에 "doing"은 없다
```

`status` 어휘를 여섯 벌에서 한 벌로 통일하던 3편의 그 작업에서, **대시보드의 필터를 같이 안 고쳤다.** "감상 중 미디어"는 `doing`을, "안 읽은 스크랩"은 `unread`를, "미발행 초고"는 `published`를 아직 찾고 있다. 셋 다 지금은 존재하지 않는 값이라 영원히 빈 표다.

빈 표는 에러가 아니다. 그냥 "오늘은 감상 중인 게 없구나" 하고 넘어가게 된다. **속성 기반 시스템의 실패는 시끄럽지 않다.** 이게 폴더와 가장 다른 점이고, 이 방식을 쓰겠다면 알고 시작해야 하는 부분이다.

**트리를 훑다가 우연히 발견하는 재미는 없다.** 찾는 건 잘 되는데 마주치는 건 안 된다. 그래서 무작위 노트 명령을 `⌘⇧R`에 걸어뒀는데, 솔직히 대체가 되지는 않는다.

여기까지가 넣고 찾는 얘기다. 그런데 잘 넣고 잘 찾는다고 삶이 바뀌지는 않는다. 다음 편은 **기록만 쌓이고 행동은 안 바뀌는 문제**를 다룬다.
